Partition Lab

Three devices share one record: a cabin note and a count of items sold. Cut the network between them, keep working, then reconnect. Switch modes to see what choosing consistency or availability costs during a split. The simulation runs in Rust, compiled to WebAssembly.

Every device always accepts writes. Copies may differ during a split and merge when they reconnect.

Try this

  1. Lost updates. Isolate C. Sell 2 on A and 1 on C. Reconnect all. The counter keeps all 3 sales; the plain number keeps only the last writer’s value.
  2. Concurrent edits. Isolate C, save a different note on A and on C, then reconnect. Every device settles on the same note: the one with the higher stamp.
  3. Always writable. While C is cut off it keeps accepting sales and notes. Nothing is refused; the copies just differ until they meet again.
  1. Refused writes. Isolate C and try to sell on C. It can’t reach a majority (2 of 3), so the write is refused. A and B keep working.
  2. Catching up. Sell on A while C is cut off, then reconnect. C adopts the newer version; no merging is needed because only one side could write.
  3. A lock meets a partition. Take the edit lock on C, then isolate C. C holds the lock but can’t write; A and B can’t edit the note either. Use Expire lease on A to recover.

    How each mode decides

    Availability mode: every device writes locally and merges whole states when it can reach another device. Each merge is commutative, associative and idempotent, so copies converge in any order. Excerpt from src/crdt.rs:

    // Last write wins: Stamp is (counter, device), compared in that order,
// so every replica picks the same winner for concurrent writes.
impl<T: Clone> Merge for LwwRegister<T> {
    fn merge(&mut self, other: &Self) {
        if other.stamp > self.stamp {
            self.value = other.value.clone();
            self.stamp = other.stamp;
        }
    }
}

// PN-counter: one increment and one decrement slot per device.
impl Merge for PnCounter {
    fn merge(&mut self, other: &Self) {
        for d in 0..N {
            self.inc[d] = self.inc[d].max(other.inc[d]);
            self.dec[d] = self.dec[d].max(other.dec[d]);
        }
    }
}

    Consistency mode: a write must reach a majority (2 of 3). The cut-off device refuses writes, so there is never anything to merge. Editing the note also needs the edit lock, a mutex kept in the same majority-replicated state. Simplified from Lab::cp_write in src/lib.rs:

    let group = self.net.group_of(i);
if group.len() * 2 <= N {
    return refuse("can’t reach a majority");
}
let mut next = newest_copy_in(group);
change(&mut next)?;
next.version += 1;
// copy `next` to every device in the group

    The repository includes property tests that check the merge laws, convergence after any partition, and that consistency mode never splits into two histories.
